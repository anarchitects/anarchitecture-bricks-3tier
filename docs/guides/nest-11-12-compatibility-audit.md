## Conclusion and evidence levels

Nest 12 is available: the official [v12.0.0 release](https://github.com/nestjs/nest/releases/tag/v12.0.0) exists, and the npm registry reports stable core/framework **12.1.2**, published 2026-09-30. Availability is not the blocker. The current bricks declare Nest 11 only; Nest 12 support remains **unverified and outside their declared peer ranges**.

Preserving Nest 11 while adding Nest 12 is a viable investigation path: current upstream Config, JWT, TypeORM and Passport integrations have releases whose peers include both. No package-specific need to drop Nest 11 has been established. CommonJS output alone does not establish such a need either. The outstanding gates are tooling, module loading, declarations, behavior and clean installed artifacts.

This document distinguishes:

- **Declared baseline**: checked-in package ranges and the installed versions matching `yarn.lock`. This audit does not certify a fresh runtime test pass.
- **Upstream-compatible candidate**: upstream metadata admits the combination. It has not been validated as a consuming brick application.
- **Verified support**: reserved for passing clean packed-consumer tests and CI under #468. No Nest 12 combination has this status in #462.

Registry references below pin versions rather than moving `latest` tags. Optional peers need installation only when the corresponding feature is used. A permissive peer declaration is evidence of install eligibility, not behavior.

## Node, TypeScript and Nx strategy

The [Nest migration guide](https://docs.nestjs.com/migration-guide#nodejs-requirements) gives a runtime floor of Node 20.19 or 22.12 on those lines, despite core's `>=20` engine. ESM loading is the reason; the guide explicitly allows CommonJS hosts. Generators have a higher floor. Do not infer compiler or generator support from the runtime engine.

| Scope                          | Evidence                                                                                                                                                                                                                         | Consequence                                                                                                                                      |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Current database-backed bricks | TypeORM 1.1.1 and four package engines: `^20.19.0 \|\| ^22.13.0 \|\| >=24.11.0`                                                                                                                                                  | Preserve until tested changes justify a new contract; excludes Node 21/23 but the open upper range deserves explicit support-policy review       |
| Compiler                       | Workspace TypeScript `6.0.3`; Nest core does not declare a TypeScript peer floor                                                                                                                                                 | Retain TS 6.0.3 as the initial verification compiler; consumer declaration compilation must run without `skipLibCheck` or workspace path aliases |
| Nest schematics                | [12.0.6](https://registry.npmjs.org/@nestjs/schematics/12.0.6): TypeScript `>=6.0.0`, Node `^22.22.3 \|\| ^24.15.0 \|\| >=26.0.0`                                                                                                | Generator minimums must not silently become brick runtime minimums                                                                               |
| Existing Nx plugin             | [@nx/nest 23.2.1](https://registry.npmjs.org/@nx/nest/23.2.1) and latest [23.3.0](https://registry.npmjs.org/@nx/nest/23.3.0) both declare optional common/core peers `>=10.0.0 <12.0.0`                                         | A root Nest 12 install with this plugin is outside its declared contract even though the peers are optional                                      |
| Available replacement          | [@anarchitects/nest 0.0.3](https://registry.npmjs.org/@anarchitects/nest/0.0.3): Nx/devkit `>=23.2.0 <24`, Nest CLI `>=12.0.0 <13`, Node `^22.22.3 \|\| ^24.15.0 \|\| >=26.0.0`; dependency TS `>=6.0.0 <7`, schematics `12.0.6` | Already published on npm; workspace Nx 23.2.1/TS 6.0.3 fit. Root still needs a Nest 12 strategy and CLI dependency                               |

The replacement plugin's [source README at audited revision](https://github.com/anarchitects/anarchitecture-plugins/blob/d8ebdfeaab134b3980179b0e2acb3d52fe84624d/packages/nest/README.md) explicitly supports **Nest 12 only** and requires an existing Nest 11 workspace to upgrade before `init`. It delegates compilation/start to Nest CLI, discovers `nest-cli.json`, and describes new independent libraries as source-only ESM. That workflow does not automatically preserve this repository's compiled publishable packages or existing `@nx/js:tsc`/Webpack targets.

**Preferred direction for #463:** evaluate `@anarchitects/nest` for Nest 12 workspace integration, preserving explicit publishable-library outputs and tests. Select target ownership, CLI configuration and generator defaults before adoption. Keep Nest 11 validation in isolated runtime hosts, without installing the Nest-12-only plugin there. If root migration is not yet feasible, keep root Nest 11 and run a separate Nest 12 consumer fixture; do not force incompatible peers. Runtime brick packages must not acquire Nx/plugin dependencies. This audit does not install or initialize either plugin.

For #468, separate the tooling lane (at least Node 22.22.3 or 24.15, TS 6.0.3) from runtime consumer lanes. Cover supported Node lines and advertised minimums, especially CommonJS `require(esm)`. The local audit environment was Node 24.21.0 and Yarn 4.18.0; that single environment cannot prove the engine range.

## Support and release gates

For each candidate major, #464–#468 must demonstrate the public facade and advanced entry points, deterministic `forRoot` and `forRootFromConfig`, provider overrides, optional features, compilation and app boot. Add package-specific real HTTP, mail, database/migration and authorization checks from the inventory. Record exact dependency versions, Node/TS versions, commands and CI evidence. Keep unsupported adapter or dependency combinations explicit.

Do not advertise a peer union until the admitted combinations have evidence. If a package cannot retain Nest 11, record the concrete failing API/dependency, attempted compatible alternative, affected exports and consumer migration. Retain the prior Nest 11 release line; obtain human acceptance of a breaking release rather than narrowing support silently. For current `0.x` bricks, plan a documented next-minor breaking release under the [repository release conventions](../../CONTRIBUTING.md#release-workflow-domain-groups); for a future stable package, removal of supported Nest/Node versions requires a major release. #469 owns final version/release decisions.

This audit introduces no breaking runtime changes and identifies no reason to deprecate an existing npm package version. Any later deprecation requires an established defect and explicit human approval.

Newsletter publication remains gated by [#428](https://github.com/anarchitects/anarchitecture-bricks-3tier/issues/428): no incremental npm releases during that epic; complete its implementation and acceptance gates before the coordinated Newsletter release. #467 and #469 must check that state rather than treating Nest compatibility work as permission to publish.
